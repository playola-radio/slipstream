# FD5 four-arm measurement protocol — acceptance draft

The registered command is `npm run bench:fd5 -- --config <approved copy of tools/fd5-provisional-config.json> --out /path/outside/repo/fd5-report.jsonl`. The output path must be new and outside both worktrees. The file records a start line, host samples, each completed arm with raw attempt and durable timing evidence, the large-log probe, then a final verdict or a failure line; result lines are fsynced. This command is **not authorized to run yet**: it refuses to start, before creating the output file, unless `approvalRequired.measurementWindow` holds an approved UTC window containing the current time with host vetoes approved and `approvalRequired.packetDecisions` is approved. The interface page budget is the merged 10,000 ms including queue wait; clip keeps 100 ms; C=2, Q=8, W=8. The config validator rejects any other deadline.

The driver fixes three repetitions of 100 scheduled writes at 120 ms intervals plus 100 burst writes. It rotates four arms as `baseline, clip-only, interface-only, combined`; `interface-only, combined, baseline, clip-only`; `combined, baseline, clip-only, interface-only`. Each loaded arm uses the baseline from its own repetition. This produces 54 individual latency comparisons (overall, scheduled, burst p50/p99 for three arms and three repetitions) and nine throughput comparisons. Each latency must be at most 1.20× its paired baseline; throughput at least 0.95×; both sides must have zero missing writes. Any insufficient load invalidates that comparison. No average of repetitions substitutes for a failed cell.

The campaign wall caps are fixed protocol values: every arm has exactly a 180-second cap, and corpus preparation has exactly a 2300-second cap. Brian approved the preparation cap on 2026-10-01 as 1.5x the measured 1,521-second corpus preparation, rounded up, after the initial 300-second campaign cap stopped attempt 1.

The clip load reuses B2's corpus, 16 cycling slots, immediate overload retry, 100,000-attempt guard, and `scoreCaptureArm` without changing its semantics. The interface load has its own 16 cycling slots. Each load client runs in its own worker thread so fetch/JSON loops do not delay capture's durable-boundary callback. A slot owns one immutable range/content key, retries only an HTTP `skipped/overloaded` response after a 100 ms pause, and retires all other outcomes. Corpus pages cross TS, TSX and Swift independently with 1, 4 and 16 files per page and tiny/representative source sizes; each after-content hash is unique. In every 60 pages, one page per language uses its parse-failure fixture, which must come back `incomplete` with `before-parse-error`, and one TypeScript and one TSX page use the Unicode-span fixture. Every 25th page (index 11 mod 25) is a planned client disconnect after 100, 500, 2,000 or 5,000 ms, rotating so all 12 language × delay pairs occur; a planned page is never retried and never counts toward load sufficiency. The writer, watcher, reader and durable health boundary are real. The corpus is historical synthetic reader input only; it never emits a live capture event. Load continues through the actual capture stop/drain, and all work uses fresh disposable store/worktree roots.

## Tracing and the failed overhead gate

The 2026-09-29 bounded overhead step at `a150731` failed the approved tracing tolerance (clip capture p50 1.103× and 1.066× against 1.05). The observer is unchanged, so that failure stands and is not rerun. Consequences:

- The 12 registered arms run **without** the projection-trace observer. Only they are scored against B2.
- Interface load sufficiency for those arms is decided from HTTP alone: continuous request coverage; in each 1–2 second capture window, a complete page with a ready changed row computed on this arm's fresh server plus an `overloaded` response; a key reused only after its own overload; explicit `timeout` pages counted as timeouts; any other incomplete page counted as unexplained. Each server's cache is per process and every after-content is unique, so a ready changed row on a fresh server is fresh work. Untraced timeout fractions are reported as lower/upper bounds because a look-ahead timeout is indistinguishable from a complete page without trace evidence.
- Three traced **witness** arms (clip-only, interface-only, combined) run after the 12. Their capture latency is diagnostic only. They supply the trace-only evidence: admission classification and freshness, clip cache bypass, phase timing, actual TS worker and Swift child exits, a planned disconnect that cancelled running TypeScript and Swift work (a parser process started for or retired by that unit, alive at cancellation and then exited), a retired TS worker that actually exited, and all five variant classes (three parse-failure languages, Unicode TS and TSX). Every witness must be valid.
- After every arm the driver requires that no child process of the bench remains (5 s); a failed process listing counts as a remaining child. TS workers are threads; their exits are proven only by the witnesses.
- The approval and window are rechecked before every arm and before the large-log probe. A host veto, window end or arm cap stops the active load at once; the arm's own bounded writer, drain and cleanup get at most 60 more seconds, then the campaign fails. A journal write failure stops the campaign after the record that hit it.

## Large-log probe

FD4 left one measurement risk: a page that must cross many identical paths before its only visible row. After the witnesses the driver writes one session of 8,000 changed-then-restored paths plus one real TypeScript change sorted last (about 13.9 MB and 24,000 records, inside the 16 MiB / 100,000-record scan budget), then requests it with `limit=1` three times, each on a fresh untraced reader. The probe runs under the host monitor and its own cap (preparation plus three drain bounds). Each response must validate and be either a complete ready page whose single row is the ready real change, or an explicit `timeout`; anything else, including an `identical` row, invalidates the probe. Whether timeouts are acceptable is an owner decision.

## Scoring

The scorer validates each returned file's path, source hashes, language version, hand-specified change content, and expected parse-failure reason; a `ready` page with empty/cache-only work gives zero useful comparisons. It reports overload fraction and useful comparisons/sec by language, variant coverage, and planned-disconnect outcomes. In traced witnesses, queue and running timeouts are separate, a page with completed rows and a timed-out look-ahead counts as one timed-out request, and missing or unclassified traces invalidate the denominator. A cap hit, exhausted corpus, missing response, drain failure or unverified cleanup invalidates the arm. A host veto during an arm, an arm exceeding its 180-second cap, or a remaining child process stops the campaign; nothing is rerun.

## Bounded diagnostic driver (execution not authorized)

`node tools/fd5-diag.ts --config tools/fd5-diagnostic-config.json --mode smoke --describe` checks bounds without measuring. The separate execution path requires `--execute`, a new `--out` path outside both worktrees, a clean committed head, and completed owner decisions in a copy of the frozen config. Modes are `smoke`, `overhead`, `unqueued`, `queue`, and `w-pressure`. Every mode after smoke except `w-pressure` requires the preceding valid report with `--prior`; the report must have the same head, config hash, and scorer version. `w-pressure` measures coalescing counts rather than latency, so it runs standalone and needs only the window and its runtime-hook approval. This command never enters `runFD5` or the registered 12-arm campaign.

The bounded protocol pins 28 smoke writes and at most 128 requests; eight overhead arms with 1,600 writes, at most 1,200 requests per arm and 30 seconds per arm; 350 unqueued observations at the single 10,000 ms page budget, two warmups and up to 60 cache controls (412 requests maximum), 60 seconds per cell; six queue cells with 1,200 writes, at most 2,400 requests per cell and 30 seconds per cell including drain; and 40 W groups with at most 440 authenticated requests, 15 seconds per waiter-cap cell, and a 50 ms test-only dispatch barrier. Corpus preparation has a 300-second cancellation cap. The overhead and queue clients have 1,200 cold keys per workload, a defensive 5,000-attempt shared guard, no overload retry, and a 100 ms minimum interval per slot. Corpus exhaustion or any cap hit invalidates a cell. Tracing-off arms state which evidence is unobserved and never claim full load sufficiency.

The driver retains raw HTTP, write, admission, freshness, phase and process-exit observations in a JSONL journal and syncs each cell/failure result. A missing join, missing write, failed cleanup, host veto, or absent actual worker/child exit invalidates the diagnostic. A ready result is required before a language's response-cache controls are attempted. These results are diagnostic and cannot approve D7 or waive W evidence or the full four-arm gates.

The first authorized bounded smoke passed on 2026-09-29; its v1 overhead step failed the approved latency limits and stopped the sequence. That failure remains evidence and cannot authorize a later mode. The integrated v2 interface scoring rules are in [docs/fd5-diagnostic-scoring-v2.md](docs/fd5-diagnostic-scoring-v2.md). The observer-cost issue remains open; the registered campaign above avoids depending on it rather than resolving it.
