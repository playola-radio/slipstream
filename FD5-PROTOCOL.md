# FD5 four-arm measurement protocol — recovery draft

The registered command is `npm run bench:fd5 -- --config tools/fd5-provisional-config.json --out /path/outside/repo/fd5-report.jsonl`. The output path must be new and outside both worktrees. The file records a start line, each completed arm with raw attempt and durable timing evidence, then a final verdict or a failure line; it is fsynced after each line. This command is **not authorized for a full run yet**. The recovery stop permits unit tests and a reviewed bounded smoke only with orchestrator clearance. The provisional 400 ms interface deadline in the example is diagnostic; it is not a D7 production choice.

The driver fixes three repetitions of 100 scheduled writes at 120 ms intervals plus 100 burst writes. It rotates four arms as `baseline, clip-only, interface-only, combined`; `interface-only, combined, baseline, clip-only`; `combined, baseline, clip-only, interface-only`. Each loaded arm uses the baseline from its own repetition. This produces 54 individual latency comparisons (overall, scheduled, burst p50/p99 for three arms and three repetitions) and nine throughput comparisons. Each latency must be at most 1.20× its paired baseline; throughput at least 0.95×; both sides must have zero missing writes. Any insufficient load invalidates that comparison. No average of repetitions substitutes for a failed cell.

The clip load reuses B2's corpus, 16 cycling slots, immediate overload retry, 100,000-attempt guard, and `scoreCaptureArm` without changing its semantics. The interface load has its own 16 cycling slots in this **explicit provisional configuration**. Each load client runs in its own worker thread so fetch/JSON loops do not delay capture's durable-boundary callback. A slot owns one immutable range/content key, retries only an HTTP `skipped/overloaded` response, and retires all other outcomes. Corpus pages cross TS, TSX and Swift independently with 1, 4 and 16 files per page and tiny/representative source sizes; each after-content hash is unique. Mixed-language pages belong in the separate paging diagnostic so language rates remain interpretable. The writer, watcher, reader and durable health boundary are real. The corpus is historical synthetic reader input only; it never emits a live capture event. Load continues through the actual capture stop/drain, and all work uses fresh disposable store/worktree roots.

The scorer requires correlated internal admission traces before it can classify rejected, queued, running and failed work. It validates each returned file's path, source hashes, language version and hand-specified change content; a `ready` page with empty/cache-only work gives zero useful comparisons. It reports overload fraction and useful comparisons/sec by language, and requires continuous request coverage plus a complete fresh comparison and overload in each 1–2 second capture window. Queue and running timeouts are separate; a page with completed rows and a timed-out look-ahead still counts as one timed-out request. The approved ready/incomplete look-ahead response has no HTTP timeout reason; the admission trace records the timeout separately. Missing or unclassified traces invalidate the denominator. A cap hit, exhausted corpus, missing response, drain failure or unverified cleanup invalidates the run.

## Integration prerequisites

The reader now has an optional test-only observer for admission, per-file freshness, parser use, actual process exit and phase timing. The driver collects this evidence with bounded storage and rejects missing or ambiguous joins. Phase histograms are scoped to clip, interface range/I/O, TypeScript or Swift. CAS read and hash are separate for interface files; simultaneous side reads are samples, not additive wall time. Worker and child durations are measured at their source and stamped at parent observation time, so the stamps are not a cross-process timeline. Swift child startup ends when the parent receives an internal ready marker after Node boot and module import; child lifecycle ends at actual close. A child or worker killed before readiness contributes a censored startup count, not a fabricated startup duration. HTTP completion means the server finished its response write, not that the client received it. Tracing-overhead control and coalesced-W pressure measurement remain pending. The report leaves `d7Decision` pending and cannot approve production limits.

## Bounded diagnostic driver (not yet authorized to run)

`node tools/fd5-diag.ts --config tools/fd5-diagnostic-config.json --mode smoke --describe` checks bounds without measuring. The separate execution path requires `--execute`, a new `--out` path outside both worktrees, a clean committed head, and completed owner decisions in a copy of the frozen config. Modes are `smoke`, `overhead`, `unqueued`, `queue`, and `w-pressure`. Every mode after smoke requires the preceding valid report with `--prior`; the report must have the same head and config hash. This command never enters `runFD5` or the registered 12-arm campaign.

The bounded protocol pins 28 smoke writes and at most 128 requests; eight overhead arms with 1,600 writes, 5,000 attempts and 30 seconds per arm; 350 unqueued observations, two warmups, up to 60 cache controls and a conditional 150 Swift observations (562 requests maximum), 60 seconds per cell; six queue cells with 1,200 writes, 5,000 attempts and 30 seconds per cell including drain; and 40 W groups with at most 200 authenticated same-key requests, 15 seconds per waiter-cap cell, and a 50 ms test-only dispatch barrier. Corpus preparation has a 300-second cancellation cap. The overhead and queue clients have 1,200 cold keys per workload, no overload retry, and a 100 ms minimum interval per slot. Corpus exhaustion or any cap hit invalidates a cell. Tracing-off arms state which evidence is unobserved and never claim full load sufficiency.

The driver retains raw HTTP, write, admission, freshness, phase and process-exit observations in a JSONL journal and syncs each cell/failure result. A missing join, missing write, failed cleanup, host veto, or absent actual worker/child exit invalidates the diagnostic. Queue diagnosis requires a preceding unqueued Swift fresh completion; its deadline is the smallest diagnostic point with that evidence. The conditional 800 ms Swift cells run only when all three 400 ms Swift cells have zero useful fresh completion. A ready result is required before a language's response-cache controls are attempted. The owner must set explicit tracing-overhead tolerances for capture latency, capture throughput, ready HTTP latency and ready count before execution. These results are diagnostic and cannot approve D7 or waive W evidence or the full four-arm gates.
