# B2 Clip-Latency Measurement Protocol

This protocol measures whether cold-cache reader projection work competes with live watcher capture. The harness reports measurements without emitting a performance verdict. The procedure below was fixed before the final run; the separate acceptance bar was ratified from that run at review time.

Each full run has three repetitions of each arm, paired in the fixed order baseline/saturation, saturation/baseline, baseline/saturation. Host load averages and free memory are recorded before and after each repetition. Every repetition writes 100 isolated TypeScript files at 120 ms intervals, then a burst of 100 files. The writer runs in a worker thread so the coordinator's HTTP work cannot delay writes. Missing writes stay visible in the report and are never included in percentiles. Overall, scheduled, and burst latency distributions are reported separately.

The baseline arm makes no clip request. Before the saturation writer starts, the harness opens 16 HTTP requests and keeps exactly that many request slots cycling until capture's final quiet drain completes. A completed request is replaced only by its own slot, so the load is bounded rather than an open-loop flood; the projection queue still reports its real overload decisions. Requests target prebuilt, separate historical synthetic sessions: its blobs and `file.changed` records are created with CAS and `createLog` before any arm begins. The full run creates 8,192 distinct TypeScript edits, partitioned into 64 changes per historical session to bound public event-lookup work, each a roughly 300-line function within the parser and diff budgets. Each edit changes one body constant to a unique value while retaining the function name, so the load exercises function extraction rather than ambiguous header fallback. That corpus is disclosed as reader load only; it is never presented as a live capture. Each client slot exclusively owns its current projection input key (before/after hashes, version and language). Only an explicit `skipped/overloaded` response retries that same key: admission rejected it before computation/cache insertion, so the next attempt remains cold. Every other result permanently retires the key for that repetition. The scorer verifies the per-response key trace, sequential non-overlapping attempts, and the preceding overload disposition for every repeated key; the corpus asserts unique projection input keys independently of URLs. A fresh `ReaderServer` for every repetition permits the retained corpus to be reused by a later repetition while preserving a cold cache. There is no retry backoff. A 100,000-attempt guard bounds retained measurement records; hitting it invalidates load sufficiency.

Capture uses the real `startCapture` watcher path and the real `ReaderServer`. It does not change capture budgets, debounce, or projection settings. The harness attaches a synchronous `session.health.subscribe` listener and records `process.hrtime.bigint()` for every sequence from the previous health high-water plus one through the newly announced high-water. If health ever batches multiple sequences into one notification, that one timestamp is an upper bound for each boundary in the batch; it is never an event timestamp. After the writer completes, load remains active during a bounded quiet wait and the subsequent actual `session.stop()` drain. Durable timestamp collection also remains subscribed through that drain; quiet alone never ends measurement. The harness then stops load, unsubscribes, reads the JSONL once, and joins each expected write by path plus expected SHA-256 to the matching `file.changed` record and then to its durable-sequence timestamp.

CloudEvents `time`, `observed_at_ms`, and `Date.parse(event.time)` are never used as a durable-commit proxy: they name observation/occurrence time. A write without a matching record, or whose sequence has no captured durable-boundary timestamp, is reported explicitly as missing.

For each arm/repetition the JSON report includes p50/p99 durable-boundary latency, written/matched/captured/missing counts, throughput, clip HTTP status and fallback-reason counts, clip latency, request errors, and cold-load sufficiency. It records the actual maximum outstanding request count, `ready` responses whose request intervals overlap the measured capture interval, explicit `skipped/overloaded` responses, and whether load began before the first write and ended after the final durable capture. Throughput is durably timestamped captured samples divided by elapsed monotonic time from the first write start to the final matching durable boundary. Empty latency samples use JSON `null`, not zero. Cold load is insufficient if it has fewer than 16 outstanding requests, repeats a key without a proven uncached overload, starts late or ends early, has no overlapping ready parse or no explicit overload, exhausts its corpus or attempt budget, has a request error, or exceeds the finite drain timeout. The baseline load field is explicitly not applicable because it intentionally makes no requests. Actual request intervals must continuously cover the capture interval. The interval is also split into equal windows of 1–2 seconds (one window for shorter smoke intervals); every window must contain a complete cold `ready` request and an overload completion. The report includes those per-window counts. A complete cold ready request proves parsing occurred inside that window, while overload proves recurring admission pressure. This distinguishes sustained parsing from mere HTTP occupancy without claiming measured parser CPU utilization. These conditions are diagnostic, not performance verdicts.

Run `node src/clip-bench.ts` for the full protocol. `node src/clip-bench.ts --smoke` uses a smaller writer while retaining the same cold corpus, so it can validate continuous-load lifecycle and cleanup without lowering the corpus below the sustained-load requirement. It intentionally does not meet the repetition or sample-count protocol.

Each completed repetition is also emitted as one JSON line on stderr between arms. The final aggregate stays on stdout. A later process failure therefore preserves completed measurements without adding logging inside a measured capture interval.

## Ratified B2 acceptance bar (Brian, 2026-09-19)

For each of the three matched baseline/saturation repetitions:

- Overall, scheduled, and burst capture latency p50 and p99 must each be at most **1.20×** the corresponding baseline (18 comparisons in total).
- Capture throughput must be at least **0.95×** its paired baseline.
- Both arms must have **zero missing writes**, and the saturation arm must pass every cold-load sufficiency check above.

All conditions are required. This bar applies to the full protocol, never the smoke run. The final-runtime run at `81fa5a3` passes; see `B2-MEASUREMENT-REPORT.md` for measurements, comparisons, shared-host limitations, and the ratification record. Ratification changes no capture or projection budget.
